S3Simple Storage Service

  • 01Fondamentaux

    • Stockage objet (pas bloc, pas fichier)
    • Durabilité 11 9s (99,999999999 %)
    • Événements (create, delete, restore, réplication)
      • Cibles : Lambda, SNS, SQS
    • Piège Pas de scripting serveur (PHP, JSP, ASP.NET)
    • Cas d'usage
      • Stockage et distribution de contenu (+ CloudFront)
      • Backup / archive → lifecycle vers Glacier
      • Data lake, big data
      • DR avec CRR (réplication asynchrone entre régions)
      • Site web statique

  • 02Buckets

    • Nom globalement unique (tous comptes, toutes régions)
      • 3–63 caractères
      • minuscules, chiffres, tirets
      • pas de majuscules ni d'underscore
    • Bucket régional : choix selon latence, coût, réglementation
    • Piège Nom et région non modifiables après création
    • URL virtual-host-style
      • bucket.s3.<region>.amazonaws.com/<key>
    • Pas de vrais dossiers : des préfixes dans la clé
      • 2021/math/john.txt → filtrer par préfixe
    • Unité de facturation et de contrôle d'accès

  • 03Objets et metadata

    • Objet = data + metadata, identifié par une clé unique
    • Metadata système
      • Gérées par S3 : date de création, taille, version
      • Modifiables : storage class, chiffrement
    • Metadata utilisateur
      • Préfixe obligatoire x-amz-meta-
      • Stockées avec l'objet, jamais traitées par S3
    • Headers utiles à l'upload : ContentType, CacheControl (max-age=0 = pas de cache navigateur)

  • 04Opérations

    • PUT : écrit toujours l'objet entier
      • Pas de mise à jour partielle
      • Upload simple : jusqu'à 5 GB
      • Multipart recommandé dès 100 MB
      • Multipart obligatoire > 5 GB, max 5 TB
      • Parts en parallèle, reprise possible
    • GET : objet complet ou byte-range (connexion lente, traitement partiel)
    • DELETE : un ou plusieurs objets (voir versioning)
    • SDK Python : boto3.client("s3").upload_file(...)

  • 05Versioning

    • Plusieurs versions d'une même clé, chacune avec un version ID
    • Protège des écrasements, suppressions, bugs applicatifs
    • Piège Désactivé par défaut ; une fois activé, seulement suspendu, jamais désactivé
    • Chaque version est facturée
    • DELETE sans version ID
      • → delete marker devient la version courante → GET renvoie 404
    • DELETE avec clé + version ID
      • → suppression définitive de cette version
    • Requis pour Object Lock et pour la réplication

  • 06Chiffrementqui tient la clé, et qui peut lire

    Les sigles

    • SSE = Server-Side Encryption : c'est S3 qui chiffre et déchiffre
    • SSE-S3 : clé gérée par S3
    • SSE-KMS : clé gérée par KMS (Key Management Service)
    • SSE-C : clé fournie par le client (Customer-provided key)
    • Client-side (CSE) : Client-Side Encryption, c'est toi qui chiffres avant l'upload
    • AES-256 : l'algorithme utilisé (Advanced Encryption Standard, clé de 256 bits)

    Le principe : 2 clés (envelope encryption)

    Clé maîtreverrouilleClé de donnéesverrouilleTon fichier
    • Clé de données : une par objet, elle chiffre le fichier
    • Clé maître : elle chiffre la clé de données
    • S3 stocke le fichier chiffré + sa clé de données chiffrée
    • Intérêt : on protège et contrôle une seule clé maître au lieu de millions

    Les 4 modes = qui tient la clé maître

    ModeQui tient la cléToi, tu faisQui peut lire
    SSE-S3S3, invisibleRienTous ceux qui ont les droits S3
    SSE-KMSKMS, dans ton compteNommer la clé à l'uploadDroits S3 et kms:Decrypt, chaque lecture loggée
    SSE-CToi, hors AWSEnvoyer la clé à l'upload et au downloadCeux qui ont ta clé
    Client-sideToiChiffrer toi-même avant l'uploadCeux qui ont ta clé ; AWS ne voit rien

    Dans les 3 modes SSE, S3 fait le travail. Seule l'origine de la clé change.

    Tu chiffres déjà sans le savoir

    • À jour Depuis janv. 2023, SSE-S3 automatique sur tout nouvel objet
    • Transparent : S3 chiffre à l'écriture, déchiffre à la lecture
    • Vérifier : aws s3api head-object --bucket b --key k
      • "ServerSideEncryption": "AES256" = SSE-S3 ; "aws:kms" = SSE-KMS
    • Piège SSE-S3 protège contre le vol de disque, pas contre quelqu'un qui a les droits IAM
    • Donc au quotidien, ta vraie protection reste les permissions (branche 07)
    • SSE-S3 : AES-256, rotation de la clé maître automatique par S3

    Pourquoi aller plus loin que SSE-S3

    • Deuxième serrure : un dev avec s3:* voit les fichiers mais ne peut pas les ouvrir sans la clé KMS
    • Coupure d'urgence : fuite de credentials → désactiver la clé KMS, plus personne ne lit
    • Audit : CloudTrail loggue chaque usage de la clé (qui, quand, quel objet)
    • Contrôle de la clé : tu choisis qui l'utilise (key policy) et tu gères sa rotation
    • Obligation légale (banque, santé) : la clé ne doit pas être chez AWS → SSE-C ou client-side

    SSE-KMS en pratique

    • Piège Lire demande s3:GetObject et kms:Decrypt, sinon AccessDenied
    • Chaque GET/PUT appelle KMS, qui a des quotas → throttling possible
      • Solution : S3 Bucket Key (beaucoup moins d'appels KMS)
    s3.upload_file("f.pdf", "bucket", "f.pdf", ExtraArgs={
  "ServerSideEncryption": "aws:kms",
  "SSEKMSKeyId": "arn:aws:kms:...:key/abcd"})
# download : rien à préciser, S3 appelle KMS pour toi

    SSE-C en pratique

    • Clé envoyée à chaque requête, S3 l'oublie aussitôt
    • HTTPS obligatoire
    • Clé perdue = données perdues
    args = {"SSECustomerAlgorithm": "AES256",
        "SSECustomerKey": ma_cle}
s3.upload_file(..., ExtraArgs=args)
s3.download_file(..., ExtraArgs=args)  # même clé

    Client-side en pratique

    • S3 ne stocke que du texte chiffré, il ne sait même pas que c'est chiffré
    • Pourquoi : AWS ne doit jamais voir le clair (loi, contrat) ; défense en profondeur (bucket public par erreur, credentials volés → toujours illisible) ; chiffrement de bout en bout depuis la machine source
    • Coût : gestion des clés à ta charge, Athena / S3 Select / Lambda ne lisent plus le contenu, plus de code
    • Clé perdue = données perdues
    • Outils : Amazon S3 Encryption Client, AWS Encryption SDK (jamais son propre algo)
    • La clé maître peut rester dans KMS, le chiffrement se fait quand même en local
    chiffre = mon_chiffrement(open("f.pdf","rb").read(), ma_cle)
s3.put_object(Bucket="bucket", Key="f.pdf", Body=chiffre)

    En transit et règles imposées

    • HTTPS / TLS
      • À jour TLS 1.2 minimum
    • Forcer HTTPS : Deny si aws:SecureTransport = false
    • Forcer un chiffrement : Deny si le header x-amz-server-side-encryption ≠ AES256 / aws:kms
    • Changer le chiffrement par défaut ne rechiffre pas les objets existants

    Lequel choisir

    • Site statique, assets publics → SSE-S3 (rien à faire)
    • Données sensibles, audit, révocation → SSE-KMS
    • Clé hors d'AWS, mais AWS chiffre → SSE-C
    • AWS ne doit rien voir en clair → client-side

  • 07Contrôle d'accèsqui peut faire quoi, et qui gagne en cas de conflit

    Les 3 types et quand les utiliser

    TypeAttaché àUtiliser quand
    Policy IAM
    identity-based    		User, groupe, rôleUne identité de ton compte accède au bucket (ex. rôle d'une Lambda). Cas le plus courant.
    Bucket policy
    resource-based    		Le bucket (JSON)Accès public, accès cross-account, ou règle pour tous (HTTPS, chiffrement, VPC endpoint, IP)
    ACL
    resource-based    		Bucket ou objet (XML)Ne plus utiliser. Théorie d'examen seulement.

    Ton code dans ton compte → IAM. Public, cross-account ou règle globale → bucket policy. ACL → oublier.

    • ACL, pour la théorie : c'était le seul moyen de gérer un objet uploadé par un autre compte (le bucket owner ne le possédait pas). Réglé par Bucket owner enforced.
    • Bucket policy = même langage JSON qu'IAM, avec en plus un champ Principal (qui)

    Qui gagne : l'ordre d'évaluation

    • Les policies ne s'annulent pas, AWS les évalue toutes ensemble
    • 1. Refus implicite : aucun Allow nulle part → refusé
    • 2. Un seul Allow suffit (même compte) : IAM ou bucket policy
    • 3. Un Deny explicite gagne toujours, même contre 10 Allow
    • Exemple : rôle IAM avec s3:* + bucket policy qui refuse le HTTP → requête HTTP refusée

    Cross-account

    • Piège Un seul Allow ne suffit plus : il en faut des deux côtés
      • Bucket policy du compte A autorise le compte B
      • Policy IAM de l'identité du compte B autorise l'action

    Au-dessus de tout

    • Tout est privé par défaut
    • Block Public Access (bucket ou compte) : bloque une bucket policy "Principal": "*" même valide
    • À jour Object Ownership = Bucket owner enforced par défaut depuis avril 2023 : ACL désactivées, le bucket possède tous les objets
    • Pour SSE-KMS, la key policy KMS s'ajoute : il faut aussi kms:Decrypt

    Presigned URL

    • GET ou PUT sur un objet, sans donner d'autre droit
    • Pas un 4e type : elle emprunte les permissions de celui qui la signe (sans droit → 403)
    • Max 7 jours (credentials d'IAM user)
    • Signée par un rôle / STS : expire au plus tard avec la session

    CORS

    • Du JS chargé depuis un autre domaine appelle le bucket → le navigateur exige CORS
    • Config JSON : AllowedOrigins, AllowedMethods, AllowedHeaders, MaxAgeSeconds
    • Max 100 règles

    Exemples concrets

    1. Policy IAM sur le rôle d'une Lambda (ton compte)

    { "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::mon-bucket/*" }

    2. Bucket policy : lecture publique (site statique)

    { "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::mon-bucket/*" }

    3. Bucket policy : cross-account (+ Allow IAM côté compte B)

    { "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::222233334444:root" },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::mon-bucket/*" }

    Exemples : imposer une règle avec Deny

    4. Refuser tout accès sans HTTPS

    { "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::mon-bucket",
               "arn:aws:s3:::mon-bucket/*"],
  "Condition": { "Bool":
    { "aws:SecureTransport": "false" } } }

    5. Refuser un upload qui n'est pas en SSE-KMS

    { "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::mon-bucket/*",
  "Condition": { "StringNotEquals":
    { "s3:x-amz-server-side-encryption": "aws:kms" } } }

    Resource : mon-bucket = le bucket lui-même (ListBucket) ; mon-bucket/* = les objets (Get/Put/Delete).

  • 08Site web statique

    • S3 website hosting seul
      • bucket.s3-website-<region>.amazonaws.com
      • Bucket public + bucket policy
      • index.html / error.html, redirections
      • HTTP seulement
    • S3 + CloudFront (prod)
      • Bucket privé, accès via OAC (remplace OAI)
      • HTTPS + domaine custom
      • Certificat ACM en us-east-1
    • Amplify Hosting : S3 + CloudFront managés + CI/CD Git
    • Déployer : aws s3 sync ./build s3://bucket --delete puis invalidation CloudFront

Les réflexes pour l'examen

  1. Fichier > 5 GB → multipart obligatoire. Dès 100 MB → multipart recommandé.
  2. Modifier un bout d'objet → impossible, on réécrit l'objet entier.
  3. Supprimé par erreur avec versioning → retirer le delete marker.
  4. Versioning ne se désactive pas, il se suspend.
  5. Deny explicite quelque part → toujours refusé.
  6. Autre compte AWS doit accéder → bucket policy + Allow IAM côté B.
  7. Bucket policy publique sans effet → Block Public Access activé.
  8. Accès temporaire à un objet sans créer d'user IAM → presigned URL.
  9. Presigned URL qui expire trop tôt → signée avec des credentials temporaires.
  10. Audit de qui a utilisé la clé → SSE-KMS.
  11. AccessDenied sur un objet SSE-KMS malgré les droits S3 → manque kms:Decrypt.
  12. Throttling KMS sur S3 → S3 Bucket Key.
  13. Clé hors d'AWS mais chiffrement par AWS → SSE-C.
  14. AWS ne doit jamais voir les données en clair → client-side.
  15. Erreur CORS dans le navigateur → configurer CORS sur le bucket.
  16. Site en HTTPS → CloudFront, pas le website endpoint.
  17. Déclencher un traitement à l'upload → S3 event → Lambda / SQS / SNS.
  18. Ressource arn:aws:s3:::bucket ≠ bucket/* : ListBucket vise le bucket, GetObject vise les objets.
  19. SSE-S3 ne protège pas contre un accès IAM trop large : ce sont les permissions qui protègent.
