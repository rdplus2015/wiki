  • 01Serverless et Lambda

    Pourquoi le serverless

    • Le cloud permet d'abstraire la couche infrastructure pour se concentrer sur la logique métier
    • Niveaux d'abstraction : on-premises → serveurs virtuels → conteneurs → serverless
    • Serveurs classiques : tu gères les instances, les correctifs de l'OS, la plateforme, le scaling, la sécurité. Serverless : tu construis, déploies et surveilles
    • Tu paies le temps d'exécution du code, pas la capacité au repos
    • Principe moderne : petites pièces faiblement couplées, bases de données dédiées, services managés pour l'intégration, infrastructure as code
    • Monolithe : simple au départ, mais une seule pile techno, une seule base dimensionnée pour le pire cas, un pipeline de livraison partagé. Microservices : chaque pièce évolue seule, au prix d'une courbe d'apprentissage

    Lambda

    • Service de calcul serverless : exécute ton code sans provisionner ni gérer de serveur
    • Invoque ton code en réponse à des événements
    • Scale automatiquement
    • Logs et métriques intégrés via CloudWatch
    • Paiement au temps de calcul utilisé, rien au repos
    • Ton code : Node.js, Python, Ruby, Java, Go, .NET, ou un runtime personnalisé

    Deux composants

    • Event source : ce qui publie des événements vers Lambda
    • Function : ton code, exécuté quand la source déclenche

    Les 6 atouts

    • Apporter son propre code
    • S'intègre aux autres services AWS et les étend
    • Modèles flexibles de ressources et de concurrence
    • Modèle de permissions flexible
    • Disponibilité et tolérance aux pannes intégrées
    • Plus de ressources inactives à payer

    Cas d'usage

    • Application web : S3 (front statique) → API Gateway → Lambda → DynamoDB → réponse
    • Flux temps réel : Kinesis → Lambda traite les nouveaux records → résultats dans DynamoDB
    • Backends web, mobile, IoT, API tierces
    • Traitement de données à chaque changement d'état : upload S3, écriture DynamoDB, alarme CloudWatch, horaire
    • Chatbots (Lex) et skills Alexa
    • Automatisation IT : démarrer/arrêter des EC2, mettre à jour des security groups

  • 02La fonction et la concurrence

    Ce qui compose une fonction

    • Permissions d'accès : qui l'invoque, ce qu'elle a le droit de faire
    • Événements déclencheurs
    • Runtime et package de déploiement : ton code et ses dépendances
    • Configuration : mémoire, timeout, variables d'environnement…

    Environnements éphémères

    • Chaque invocation tourne dans un environnement créé à la demande, de courte durée, puis supprimé
    • Tu ne le contrôles pas : Lambda gère son cycle de vie

    Concurrence

    • Concurrence = nombre d'invocations qui tournent en même temps. Lambda crée de nouveaux environnements pour suivre le rythme
    • Reserved concurrency : plafond optionnel par fonction, pris sur le quota régional. Empêche une fonction d'affamer les autres ou de submerger un système en aval
    • Quota régional : limite souple du total des invocations simultanées, 1 000 par défaut par compte et par Région
    • Montée en charge : limite sur la vitesse à laquelle la concurrence peut grimper lors d'un pic
    • Cadence des requêtes × durée de chaque exécution
    • La source d'événements : chaque service gère à sa façon la concurrence de ses invocations
    • Précision Depuis fin 2023, chaque fonction monte de 1 000 environnements toutes les 10 s (jusqu'au quota du compte). Les anciens « burst limits » régionaux ne s'appliquent plus tels quels

  • 03Invocationpush synchrone, push asynchrone ou pull

    Les 3 modes

    Push synchronePush asynchronePull (polling)
    Qui appelleLa source invoque Lambda directement, l'appelant attend la réponseLa source dépose l'événement, Lambda le met en file, la source repart (« envoie et oublie »)La source met l'info dans un stream ou une file ; Lambda va la chercher et invoque en lots
    Invocation typeRequestResponseEventVia un event source mapping
    Statut HTTP200202 (accepté, pas « réussi »)n/a
    RetryAucun côté Lambda : c'est ton code qui réessaie0 à 2 retries automatiques, puis DLQ ou destination OnFailureSelon la source (voir plus bas)
    ExemplesAPI Gateway, ELB (ALB), Cognito, Lex, Alexa, CloudFront, FirehoseS3, SNS, SES, CloudWatch Logs, CloudWatch Events / EventBridge, ConfigDynamoDB Streams, Kinesis, SQS
    • Piège Quand un service AWS déclenche Lambda, tu n'as aucun contrôle sur le type d'invocation : il est prédéfini par la source

    Pull : stream ou file

    • Stream (DynamoDB Streams, Kinesis) : records organisés en shards, Lambda lit un shard et invoque par lots
      • En cas d'échec, Lambda bloque la lecture du shard jusqu'à ce que le lot réussisse ou expire (24 h)
      • Parade : une destination OnFailure pour contourner un record qui échoue toujours
    • File (SQS) : en cas d'échec, le message redevient visible et est retenté, jusqu'à la limite de retries ou la rétention. Les messages qui échouent toujours vont dans une DLQ
    • Le lien source ↔ fonction est un event source mapping (CreateEventSourceMapping)
    • Le polling lui-même est gratuit : tu ne paies que les actions qui en résultent

    Invoquer à la main

    # Synchrone
aws lambda invoke --function-name my-function \
  --payload '{...}' response.json
# → {"StatusCode": 200}

# Asynchrone
aws lambda invoke --function-name my-function \
  --invocation-type Event --payload '{...}' response.json
# → {"StatusCode": 202}
    • Précision Avec l'AWS CLI v2, un payload JSON brut demande --cli-binary-format raw-in-base64-out

  • 04Permissionsdeux questions distinctes, toutes deux via IAM

    Le schéma

    Source d'événements→ peut invoquer ?Lambda→ peut agir sur ?Service ou ressource AWS
    QuestionRéponseOù
    Qui peut m'invoquer ?Resource policy (lambda:InvokeFunction)Attachée à la fonction
    Que peut faire ma fonction ?Rôle d'exécutionRôle IAM, utilisé par la fonction

    1. Resource policy : qui peut invoquer

    • Donne à une source d'événements l'action lambda:InvokeFunction
    • Pour une source hors Lambda comme S3, la permission équivalente peut vivre sur l'autre ressource (le bucket) plutôt que sur la fonction
    • Permet l'invocation cross-account (le bucket du compte A invoque une fonction du compte B)
    { "Effect": "Allow",
  "Principal": { "Service": "s3.amazonaws.com" },
  "Action": "lambda:InvokeFunction",
  "Resource": "arn:aws:lambda:...:function:ma-fonction",
  "Condition": { "ArnLike":
    { "AWS:SourceArn": "arn:aws:s3:::mon-bucket" } } }

    2. Rôle d'exécution : ce que la fonction peut faire

    • Policy IAM : les actions permises sur d'autres ressources (écrire dans DynamoDB, lire SQS, écrire les logs CloudWatch). « Qui a le droit de faire quoi »
    • Trust policy : quelle entité peut assumer le rôle. Sans elle, même si le rôle existe, personne ne peut l'utiliser. « Qui peut l'endosser »
    // Trust policy du rôle
{ "Effect": "Allow",
  "Principal": { "Service": "lambda.amazonaws.com" },
  "Action": "sts:AssumeRole" }
    • Précision iam:PassRole est exigé de l'identité qui crée ou modifie la fonction (celle qui « passe » le rôle), pas de Lambda elle-même
    • Piège Une source en polling (stream, file) utilise le rôle d'exécution pour lire, pas une resource policy

  • 05Le handler

    • Point d'entrée que Lambda appelle : handler(event, context)
    • Chaque langage a sa convention pour le désigner dans le package. Python : module.fonction (ex. app.lambda_handler)
    • event : ce qui a déclenché la fonction. Sa forme dépend de la source
      • API Gateway : chemin, query string, corps de la requête
      • S3 : bucket et objet concernés
      • Peut aussi être un objet de test que tu définis
    • context : informations d'exécution générées par AWS, variables selon le langage. Au minimum :
      • awsRequestId (Python : aws_request_id) : identifie une invocation, utile pour le support AWS
      • logStreamName : le log stream CloudWatch de l'invocation
      • getRemainingTimeInMillis() : ms restantes avant le timeout

  • 06Configuration

    Performance

    RéglageCe qu'il contrôle
    Mémoire128 MB à 10 240 MB. Le CPU est proportionnel à la mémoire
    Timeout1 s à 15 min. Évite le coût d'une fonction bloquée
    Concurrence1 000 invocations simultanées par compte et par Région (limite souple). Possibilité de réserver une part à une fonction
    Provisioned concurrencyGarde des environnements pré-chauffés pour éviter les cold starts. Facturé à part
    MonitoringX-Ray (active tracing) et CloudWatch Lambda Insights

    Prix

    • Facturation : nombre de requêtes + durée
    • Le prix par milliseconde monte avec la mémoire…
    • …mais plus de mémoire = plus de CPU = durée plus courte. Pour du travail lié au CPU, une mémoire plus haute peut donc coûter moins cher
    • Utilitaire power tuning pour trouver la mémoire qui minimise le coût total

    Ressources

    RéglageCe qu'il contrôle
    TriggersLes sources d'événements qui invoquent la fonction
    PermissionsQui l'invoque, ce qu'elle peut atteindre
    DestinationsOù va le résultat d'une invocation async, en succès ou en échec : topic SNS, file SQS, autre Lambda, bus EventBridge
    Invocation asyncNombre de retries (0 à 2), âge max d'un événement (jusqu'à 6 h), DLQ
    VPCAccès aux ressources d'un VPC privé (bases, caches, services internes)
    State machinesMachines Step Functions qui peuvent l'invoquer
    Database proxiesRDS Proxy : mise en commun des connexions
    File systemsMontage d'un système de fichiers EFS

    Code

    • Runtime : langage et version, ou runtime personnalisé
    • Variables d'environnement : paires clé-valeur lues par le code sans le modifier. Bonnes pour la config et pour des valeurs sensibles non secrètes ou chiffrées avec KMS
    • Tags : suivi et filtrage des coûts
    • Code signing : garantit que le code vient d'une source approuvée et n'a pas été altéré

  • 07Bonnes pratiques

    Concevoir la fonction

    • Sans état : ne jamais supposer qu'une donnée en mémoire survit entre deux invocations
    • Seulement le nécessaire : package et dépendances minimaux, pas tout un SDK pour deux modules. Moins de dépendances = démarrage plus rapide
    • Réutiliser l'environnement : initialiser les ressources coûteuses (connexion à une base, client SDK) hors du handler, pour que les invocations « chaudes » les réutilisent

    Écrire le code

    • Séparer la logique métier du handler : plus portable, plus facile à tester
    • Fonctions modulaires, à usage unique
    • Ajouter des logs (écrits dans CloudWatch) et renvoyer un résultat
    • Variables d'environnement plutôt que valeurs en dur (nom de bucket ou de table)
    • Piège Pas de code récursif : une fonction qui s'invoque elle-même peut s'emballer via la concurrence
    • Piège Ne pas appeler une Lambda depuis une autre : utiliser des destinations ou orchestrer avec Step Functions

  • 08Déploiement : package, versions, alias, layers

    Deux types de package

    .zipImage conteneur
    PrincipeChoisir un runtime, compresser code et dépendances, uploaderChoisir runtime et distribution Linux, emballer le code dans une image, la pousser dans ECR
    Mise en ligneÉditeur de la console, package depuis l'IDE, ou zip déposé sur S3 puis référencéLambda tire l'image d'ECR, l'optimise, la déploie : statut PENDING puis ACTIVE
    Limites50 MB zippé (upload direct) ; 250 MB décompressé avec les layers ; 3 MB dans l'éditeur console ; 512 KB par fichier individuelJusqu'à 10 GB (voir branche 11)

    Créer et mettre à jour (CLI)

    aws lambda create-function \
  --function-name my-function --runtime python3.13 \
  --zip-file fileb://my-function.zip \
  --handler app.lambda_handler \
  --role arn:aws:iam::123456789012:role/MonRole

aws lambda update-function-code \
  --function-name my-function \
  --zip-file fileb://my-function.zip
    • Précision L'exemple du cours utilise nodejs10.x, un runtime retiré depuis longtemps. Prends un runtime actuellement supporté

    Versions et alias

    • Version : instantané immuable du code + de la configuration. Seule $LATEST existe tant qu'on ne publie pas. Chaque version publiée (1, 2…) a son propre ARN
    • Piège Une fois publiée, une version ne peut plus être modifiée
    • Alias : pointeur mutable et nommé vers une version (DEV, TEST, PROD), avec son propre ARN
    • Promouvoir ou revenir en arrière = repointer l'alias, sans changer le code
    • Piège Brancher les services (notification S3, intégration API Gateway) sur l'alias et non sur une version : sinon il faut modifier la config de chaque service à chaque déploiement

    Layers

    • Archive .zip de bibliothèques, de runtime personnalisé ou de dépendances partagées, attachable sans les intégrer au package
    • Maximum 5 layers par fonction, 250 MB au total décompressé (fonction + layers)
    • Garde les packages petits (éditable dans la console sous 3 MB pour Node.js, Python, Ruby) et partage une dépendance entre plusieurs fonctions
    • AWS publie un layer public NumPy / SciPy pour Python

    Runtimes personnalisés

    • Pour un langage non supporté. Une runtime interface reçoit les événements et envoie les réponses
    • Le fichier bootstrap est le point d'entrée. Livrable avec le code ou comme layer

  • 09Surveillance et débogage

    CloudWatch

    • Logs, métriques et événements dans une vue unifiée. Logs lus comme un flux chronologique
    • Logs Insights : requêtes interactives sur les logs
    • Métriques par défaut, alarmes sur seuils avec actions automatiques

    Structure des logs Lambda

    • Un log group par fonction : /aws/lambda/<nom-fonction>, créé à la première invocation (ou à la config de la provisioned concurrency)
    • Log streams organisés par date, version de fonction et ID unique
    • Chaque invocation a un RequestId et 3 lignes clés :
      • START : début
      • END : fin
      • REPORT : durée facturée, mémoire configurée, mémoire utilisée et, si présent, Init Duration = cette invocation a payé un cold start

    X-Ray

    • Suit une requête à travers les composants de l'application et dessine une service map
    • Activation en un clic pour Lambda ; le SDK X-Ray capte les appels faits avec le SDK AWS
    • Distribution visuelle des latences, isolement des valeurs aberrantes, filtrage par type d'erreur
    ÉlémentRôle
    SegmentTravail d'une ressource de calcul : nom, détails de la requête, sous-segments
    SubsegmentDécoupage plus fin : appel à une base, une API externe, un service AWS, ou un bloc de code
    AnnotationsPaires clé-valeur indexées, utilisables dans les expressions de filtre pour chercher et grouper
    MetadataPaires de tout type, non indexées, pour du contexte qu'on ne cherchera pas
    • Piège Annotation = on peut chercher dessus. Metadata = non

  • 10Cas appliqué : le handler du fraud-detector

    Les 7 étapes

    • 1. Lire l'event : avec l'intégration proxy, le corps HTTP arrive comme une chaîne JSON dans event["body"], jamais déjà parsé
    • 2. Extraire avec .get() : body["user_id"] lève une KeyError si le champ manque. body.get("user_id", "unknown") dégrade proprement. Le défaut « unknown » est un raccourci temporaire, avant Cognito
    • 3. Ne jamais faire confiance au client pour l'identité ni l'heure : transaction_id et timestamp sont générés côté serveur, sinon un client pourrait fabriquer des IDs, provoquer des collisions ou antidater
    • 4. Construire les clés avec de simples f-strings
    • 5. Valider avant d'écrire : échouer vite avec un 4xx clair
    • 6. Écrire : table.put_item(Item=item), la seule ligne qui touche DynamoDB. Tout ce qui précède se teste sans base
    • 7. Toujours renvoyer une réponse valide : statusCode et body au minimum, avec body en chaîne JSON, pas un dict

    Le code

    body = json.loads(event["body"])
user_id = body.get("user_id", "unknown")
amount = body.get("amount")
merchant = body.get("merchant")

if amount is None or merchant is None:
    return build_response(400,
      {"error": "amount and merchant are required"})

transaction_id = str(uuid.uuid4())
timestamp = (datetime.now(timezone.utc)
  .isoformat(timespec="seconds")
  .replace("+00:00", "Z"))

pk = f"USER#{user_id}"
sk = f"TXN#{timestamp}#{transaction_id}"
table.put_item(Item=item)
    def build_response(status_code, data):
    return {
      "statusCode": status_code,
      "headers": {
        "Access-Control-Allow-Origin": "*",
        "Access-Control-Allow-Headers": "Content-Type",
        "Access-Control-Allow-Methods": "GET,POST,OPTIONS"
      },
      "body": json.dumps(data)
    }
    • Les en-têtes CORS sont renvoyés par la Lambda elle-même (voir les cartes DynamoDB et API Gateway)
    • Précision À l'écriture, boto3 refuse les float : TypeError: Float types are not supported. Use Decimal types instead. Parser avec json.loads(event["body"], parse_float=Decimal)

  • 11Hors de tes notesà connaître pour le DVA-C02

    Limites à connaître

    • Payload d'une invocation synchrone : 6 MB (requête et réponse)
    • Payload d'une invocation asynchrone : 256 KB jusqu'en 2025, 1 MB depuis octobre 2025. Un examen ancien peut encore citer 256 KB
    • Stockage éphémère /tmp : 512 MB par défaut, jusqu'à 10 240 MB. Peut persister entre invocations « chaudes », sans garantie
    • Variables d'environnement : 4 KB au total
    • Image conteneur : jusqu'à 10 GB
    • Vitesse de calcul : environ 1 769 MB de mémoire = 1 vCPU
    • Gratuit chaque mois : 1 million de requêtes + 400 000 GB-secondes

    Erreurs et retries, en détail

    • Piège Pour une fonction déclenchée par SQS, la DLQ se configure sur la file source, pas sur la fonction. Le réglage DLQ de la fonction ne vaut que pour l'invocation asynchrone
    • Les destinations (succès / échec) sont préférées à la DLQ : elles portent plus d'informations
    • Streams, réglages de l'event source mapping : BisectBatchOnFunctionError, MaximumRetryAttempts, MaximumRecordAgeInSeconds, ReportBatchItemFailures
    • SQS : le visibility timeout de la file doit valoir au moins 6× le timeout de la fonction. Partial batch response pour ne retenter que les messages en échec
    • Throttling (concurrence atteinte) : erreur 429 TooManyRequestsException en synchrone ; en asynchrone, Lambda retente pendant jusqu'à 6 h

    Concurrence et démarrage

    • Reserved concurrency : sans frais, garantit une capacité et plafonne la fonction. La mettre à 0 coupe la fonction (utile en urgence)
    • Provisioned concurrency : payante, contre les cold starts
    • SnapStart : réduit le cold start en restaurant un instantané de l'environnement initialisé (Java, et aussi Python et .NET)
    • Le cold start dépend de la taille du package, du runtime et de l'initialisation hors handler

    Réseau et sécurité

    • Piège Lambda dans un VPC : pas d'accès à Internet (ni aux API AWS publiques) sans NAT gateway ou endpoints VPC. La fonction a aussi besoin des droits pour créer ses interfaces réseau
    • Piège Pas de logs dans CloudWatch ? Le rôle d'exécution n'a pas les droits d'écriture (politique AWSLambdaBasicExecutionRole)
    • Secrets : variables d'environnement chiffrées avec KMS, ou mieux Secrets Manager / Parameter Store
    • Appel par API Gateway : la ressource de la fonction doit autoriser apigateway.amazonaws.com. Si la fonction est désignée par une variable de stage, ajouter la permission à la main (aws lambda add-permission)

    Déploiement progressif

    • Un alias pondéré répartit le trafic entre deux versions (ex. 90 % / 10 %) : un canary natif
    • SAM : AutoPublishAlias et DeploymentPreference pilotent CodeDeploy pour des déploiements progressifs

    Autres déclencheurs

    • Function URL : endpoint HTTPS dédié à la fonction, avec auth AWS_IAM ou NONE, sans API Gateway
    • EventBridge : appel planifié (cron / rate)

    Métriques CloudWatch utiles

Les réflexes pour l'examen

  1. Lambda tourne sur événement et se paie en requêtes + durée, rien au repos. Maximum 15 min par exécution.
  2. Mémoire de 128 à 10 240 MB, le CPU suit la mémoire. Plus de mémoire peut coûter moins cher (power tuning).
  3. Cold start → provisioned concurrency (payante) et initialisation hors du handler. Init Duration dans REPORT = cold start.
  4. Service AWS qui déclenche Lambda → type d'invocation imposé : API Gateway / ALB = synchrone, S3 / SNS / EventBridge = asynchrone, SQS / Kinesis / DynamoDB Streams = polling.
  5. Synchrone : pas de retry Lambda, c'est le client qui réessaie. Asynchrone : 2 retries puis DLQ ou destination OnFailure.
  6. Statut 200 = synchrone réussi. 202 = asynchrone accepté, pas encore exécuté.
  7. Stream en échec → le shard est bloqué jusqu'à résolution : OnFailure, bisect, limite de retries.
  8. Fonction déclenchée par SQS → la DLQ se met sur la file SQS.
  9. Qui peut invoquer la fonction → resource policy (lambda:InvokeFunction). Ce que la fonction peut faire → rôle d'exécution.
  10. Rôle d'exécution = policy IAM + trust policy (lambda.amazonaws.com). Pas de logs → manque la politique d'écriture CloudWatch.
  11. Lambda qui lit une file ou un stream → permissions sur le rôle d'exécution, pas sur la resource policy.
  12. Invocation cross-account → resource policy sur la fonction (ou sur la ressource source).
  13. Quota 1 000 simultanés par Région. Reserved concurrency = plafond + garantie, protège la base en aval. À 0 elle coupe la fonction.
  14. Erreur 429 TooManyRequestsException → throttling.
  15. Version = immuable. Alias = pointeur mutable. Brancher les sources sur l'alias. Alias pondéré = canary.
  16. Dépendances partagées → layers (5 max, 250 MB au total décompressé).
  17. Zip : 50 MB zippé, 250 MB décompressé. Image conteneur : jusqu'à 10 GB via ECR.
  18. Config sensible → variables d'environnement chiffrées KMS (4 KB max) ou Secrets Manager.
  19. Lambda dans un VPC sans accès Internet → NAT gateway ou endpoints VPC.
  20. Une Lambda n'en appelle pas une autre directement → destinations ou Step Functions. Pas de récursion.
  21. Tracer entre services → X-Ray. Annotations indexées, metadata non. Retard sur un stream → IteratorAge.
  22. Avec API Gateway, body doit être une chaîne JSON, sinon 502. Les en-têtes CORS se renvoient depuis la Lambda.
