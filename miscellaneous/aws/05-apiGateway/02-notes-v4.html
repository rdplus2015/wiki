  • 01Les API et la passerelle

    Une API

    • Abstrait l'implémentation : le consommateur ignore comment le fournisseur travaille
    • N'expose que le nécessaire : une surface contrôlée, pas tout le système
    • Établit un protocole de communication entre fournisseur et consommateur
    • Flux typique : client → serveur web (API) → base de données, l'API traduit dans les deux sens
    • Protocoles possibles : SOAP, WebSockets, HTTP, HTTPS
    • Codes de statut : 20x succès, 40x erreur client, 50x erreur serveur

    REST et RESTful

    • REST : un style d'architecture (sans état, URI = ressources, verbes HTTP standard)
    • RESTful : une API qui respecte ces principes. Dans la pratique, les deux mots se confondent

    API Gateway

    • Service managé et serverless, la « porte d'entrée » de tes backends
    • Fonctionne comme un videur : limite le débit, valide les clés, route selon l'origine, rejette les requêtes invalides avant le backend
    • Peut fronter : Lambda, EC2, tout autre service AWS, des endpoints VPC, un système on-premises (via Direct Connect)
    • Facturation : par appel reçu + données sortantes, aucun serveur à gérer

  • 02Types d'APIREST, HTTP ou WebSocket

    REST APIHTTP API
    EspritContrôle complet, fonctions avancéesLéger, orienté proxy
    CoûtPlus élevéLatence plus basse, jusqu'à ~70 % moins cher
    ExclusifMock, transformation fine (VTL), usage plans, API keys, resource policies, cache, génération de SDK client, endpoints edge et privésParamètre mapping, auto-déploiement
    Choisir siFonctions avancées, monétisation, API privée au VPCSimple passage vers Lambda ou un backend HTTP

    Règle : HTTP API par défaut, REST API seulement si tu as besoin d'une de ses fonctions.

    WebSocket API

    • Bidirectionnelle : chaque côté peut envoyer un message à tout moment (pas de requête/réponse)
    • Efficace pour les applications « bavardes » en temps réel : chat, tableaux de bord en direct, multijoueur
    • WSS = la variante sécurisée (TLS) du protocole
    • Il faut définir des route keys : $connect, $disconnect, $default, plus des routes personnalisées via une route selection expression (ex. $request.body.action)

    Gérer l'API

    • Développer : console, CLI, ou import/export d'une définition OpenAPI (Swagger)
    • Déployer : SAM, CloudFormation ou CDK

  • 03Créer une API REST

    URL d'appel

    https://{restapi_id}.execute-api.{region}
        .amazonaws.com/{stage_name}/
    • Générée automatiquement, sauf si tu configures un domaine personnalisé

    Routes et méthodes

    GET  /products        → liste des produits
GET  /products/{id}   → un produit
PUT  /products/{id}   → mise à jour d'un produit
    • Une route = méthode HTTP + chemin, reliée à une intégration (Lambda, HTTP, service AWS…)

    Variable gloutonne

    • {proxy+} : route fourre-tout (ex. ANY /{proxy+}), tout chemin et toute méthode vers une seule intégration
    • Souvent une Lambda qui fait son propre routage. Évite de déclarer chaque route

    Mock endpoint

    • API Gateway renvoie une réponse prédéfinie, sans appeler de backend
    • Utile pour prototyper un frontend avant que le backend existe
    • Sert aussi à gérer les requêtes preflight CORS (OPTIONS)

    Import / export

    • Une API REST ou HTTP se décrit en OpenAPI : import en bloc, ou export pour le versionnement et la portabilité

    Lambda proxy : la forme obligatoire

    • Piège La Lambda doit renvoyer exactement cette forme, avec body en chaîne. Sinon API Gateway renvoie une erreur 502
    {
  "statusCode": 200,
  "headers": { "Content-Type": "application/json" },
  "body": "{\"message\": \"ok\"}",
  "isBase64Encoded": false
}
    • Exemple d'erreur 403 : statusCode: 403, body: "{\"error\": \"Forbidden\"}"
    • Avec le proxy, les en-têtes CORS sont aussi à renvoyer par la Lambda (voir la carte DynamoDB, branche 12)

    Le trajet d'une requête

    allerMethod Request→Integration Request
    retourIntegration Response→Method Response
    • Le client entre par Method Request, le backend est appelé après Integration Request, et la réponse repart dans l'ordre inverse
    • Chaque étape est un point où API Gateway peut valider, transformer ou rejeter

    Parameter mapping (HTTP API)

    • Alternative plus légère aux templates VTL des API REST
    • Ajoute, écrase ou retire des en-têtes, query strings ou paramètres de chemin au passage
    • Exemple : injecter $context.requestId comme en-tête avant le backend

  • 06Déploiement : stages, variables, canary

    Stages

    • Un stage est une version nommée de l'API : dev, beta, prod. Son nom apparaît dans l'URL d'appel
    • Obligatoire pour REST et WebSocket : sans déploiement sur un stage, l'API n'est pas joignable
    • Automatique pour HTTP : stage par défaut, avec option d'auto-déploiement à chaque changement
    • Un stage peut représenter un environnement, chacun avec un backend différent
    • Précision Sur une API REST, une modification n'est visible qu'après un nouveau déploiement sur le stage

    Variables de stage

    • Paire clé/valeur propre à un stage, utilisable dans la config d'une intégration
    • Exemple : ${stageVariables.lambdaAlias} vaut dev, beta ou prod selon le stage
    • La même définition d'API sert des backends différents, sans la dupliquer

    Déploiement canary

    • Envoie un petit pourcentage du trafic de production vers la nouvelle version, le reste va à la version stable
    • Config : percentTraffic (ex. 10,5 %) et, au besoin, stageVariableOverrides
    • Surveiller dans CloudWatch, augmenter petit à petit
    • Promouvoir le canary = il devient la version à 100 % du trafic, et sa config est retirée

  • 07Contrôle d'accèsse protéger du trafic indésirable et autoriser les bons appelants

    Se protéger du trafic indésirable

    MécanismeCe qu'il fait
    Resource policyLimite qui peut appeler l'endpoint : un compte AWS précis, ou une plage d'IP (ex. celle du bureau). API REST seulement
    Domaine perso + certificats clientDomaine avec certificat SSL (ACM), puis certificats clients (valides 365 jours) : le backend vérifie qu'un appel vient bien d'API Gateway, ou d'un appareil IoT de confiance
    AWS WAFPare-feu applicatif devant API Gateway. Bloque injections SQL et XSS, filtre par motif (en-têtes, corps, URI), par plage d'IP, pays ou bots. Règles gérées par AWS
    CORSRègle du navigateur pour les requêtes AJAX cross-origin (domaine, sous-domaine, port ou protocole différent). Les requêtes « simples » (GET) sont exemptées
    ThrottlingProtège contre la surcharge. Requête limitée = HTTP 429 « Too Many Requests »
    • Précision Deux choses distinctes : les certificats client générés par API Gateway (le backend vérifie l'appelant), et le mutual TLS sur un domaine personnalisé (les clients présentent un certificat validé contre un truststore)

    CORS en détail

    • Requête non simple → le navigateur envoie d'abord un preflight OPTIONS que le serveur doit approuver (origines, méthodes, en-têtes autorisés)
    • API Gateway peut gérer le preflight seul (un mock en coulisse pour REST, plus simple pour HTTP), ce qui décharge ton code
    • Piège Avec une intégration Lambda proxy, le preflight est géré, mais la vraie réponse doit porter elle-même les en-têtes CORS

    Throttling et usage plans

    • Quota Région par défaut : 10 000 requêtes/seconde pour toutes les API du compte (relevable sur demande)
    • Réglable par stage, par méthode / route, et par client via un usage plan
    • Ordre d'application, du plus précis au plus général : client + méthode → client → méthode / stage → compte
    • Usage plan (REST) : quels clients (identifiés par une API key) accèdent à quels stages, avec une limite de débit et un quota (par jour, semaine, mois). Plusieurs paliers possibles (User, Partner, Service)
    • Piège Une API key identifie et mesure un client, elle ne remplace pas une vraie authentification

    Autoriser les appelants : 4 options

    OptionPrincipeQuand
    NoneAccès ouvert à tousAPI publique
    IAML'appelant signe la requête avec des credentials AWS (souvent temporaires, via un SDK). Une requête non signée est rejetéeAppelants AWS, services internes
    JWTJeton validé derrière OIDC / OAuth 2.0. REST : Cognito user pool. HTTP : Cognito ou un autre fournisseur JWT. Vérifie le jeton et son scopeUtilisateurs d'une application web ou mobile
    Lambda authorizerUne Lambda s'exécute avant l'intégration et valide un jeton bearer (OAuth maison, SAML) ou d'autres paramètres avec ta logiqueRègles d'accès sur mesure
    • Un authorizer se configure par route, ou se partage entre routes
    • Précision Lambda authorizer : c'est l'authorizer qui renvoie le verdict (une policy IAM, ou isAuthorized true/false pour une HTTP API). La fonction cible reçoit ensuite les données context de l'authorizer, ce qui lui permet de gérer un refus proprement

  • 08Surveillance

    Métriques CloudWatch (automatiques, chaque minute)

    MétriqueSens
    CountNombre total d'appels sur la période
    IntegrationLatencyTemps de réponse du backend seul
    LatencyAller-retour complet : de la réception de la requête par API Gateway à la réponse au client
    4XXError / 5XXErrorErreurs côté client / côté serveur
    • Aucune config requise, conservées 15 mois
    • Latency moins IntegrationLatency = le temps passé dans API Gateway lui-même

    Access logs (optionnels, par stage)

    • 1. Créer un log group CloudWatch
    • 2. Le pointer dans les paramètres d'access log du stage, avec un format (Common Log Format ou JSON) : IP source, heure, méthode, route, statut, taille de réponse, ID de requête
    • Les logs d'erreur sont créés automatiquement. Les access logs demandent cette config explicite

    Les 3 autres outils

    OutilRépond à
    X-Ray« Où une transaction passe-t-elle son temps dans mon application distribuée ? » Regroupe les données de chaque service touché en une trace, avec la distribution des latences. Activable directement sur API Gateway
    Config« Cette ressource respecte-t-elle nos règles ? » Snapshot de configuration, règles de conformité, notification SNS en cas d'écart
    CloudTrail« Qui a modifié quoi, et quand ? » Activé par défaut, enregistre chaque appel d'API lié à API Gateway (console, SDK, CLI)

  • 09Optimisation

    Cache (API REST)

    • Met en cache les réponses aux GET : moins d'appels au backend, latence réduite
    • Clés de cache possibles : chemin, en-têtes, query strings
    • Réglable par stage ou par méthode, avec un TTL modifiable. Chiffrement du cache possible
    • Piège Facturé à l'heure, utilisé ou non : un coût fixe, pas du paiement à l'usage
    • Métriques : CacheHitCount (servi par le cache) et CacheMissCount (servi par le backend)

    Compression des payloads

    • Réduit les données échangées client ↔ API Gateway : moins de coût et de latence
    • Codages : deflate, gzip, identity
    • minimumCompressionSize fixe le seuil ; 0 compresse tout
    • La décompression des requêtes est active par défaut, la compression des réponses se configure
    • Piège Compresser un tout petit payload peut l'agrandir, et coûte du calcul des deux côtés : tester le bon seuil

  • 10Scénario du lab : le café

    • Application web (hébergée sur S3) qui lit et écrit la table DynamoDB FoodProducts via une API, pas directement depuis le JavaScript du navigateur
    • Démarche : 1. API avec des mock endpoints → 2. validation par les parties prenantes → 3. remplacement des mocks par de vraies intégrations (Lambda ↔ DynamoDB)
    • Le contrat public de l'API ne change pas : API Gateway reste une porte d'entrée stable que l'on peut repointer vers d'autres backends
    • Points à ne pas oublier avec ce montage : les en-têtes CORS dans la réponse de la Lambda, et la conversion des Decimal avant json.dumps (voir la carte DynamoDB)

  • 11Hors de tes notesà connaître pour le DVA-C02

    Les codes d'erreur à reconnaître

    CodeCause typique
    400Requête invalide, ou refusée par la validation de requête
    401Non autorisé : jeton absent ou invalide pour l'authorizer
    403Refusé : IAM, resource policy, WAF, API key manquante. « Missing Authentication Token » = souvent une route ou un chemin inexistant
    429Throttling : trop de requêtes
    502Réponse du backend invalide, typiquement une Lambda proxy qui ne renvoie pas la forme attendue
    504Timeout d'intégration

    Limites

    • Piège Timeout d'intégration : 29 s par défaut pour une API REST (30 s pour une HTTP API)
      • Depuis juin 2024, relevable au-delà de 29 s pour les REST régionales et privées, avec un impact possible sur le quota de débit
    • Payload max : 10 MB par requête ou réponse. Une Lambda appelée en synchrone : 6 MB
    • Throttling : 10 000 req/s en régime établi, avec un burst de 5 000 requêtes
    • Message WebSocket : 128 KB

    Authorizer et cache

    • Le résultat d'un Lambda authorizer est mis en cache : TTL par défaut 300 s (0 à 3 600 s)
    • Cache des réponses : TTL par défaut 300 s, maximum 3 600 s
    • Invalider le cache : l'appelant envoie l'en-tête Cache-Control: max-age=0, avec la permission d'invalider

    Validation et domaine perso

    • Validation de requête (REST) : paramètres, en-têtes et corps vérifiés contre un modèle JSON Schema avant d'appeler le backend → 400 sinon. Économise des invocations Lambda
    • Domaine personnalisé : certificat ACM. Endpoint edge-optimized : certificat en us-east-1. Endpoint régional : certificat dans la même Région

    WebSocket, SAM, variables

    • Pour écrire à un client connecté depuis le backend : appeler l'API @connections avec son connectionId
    • SAM : un event Api crée une API REST, un event HttpApi crée une API HTTP. sam local start-api les simule en local
    • Variable de stage qui désigne une Lambda : API Gateway doit avoir la permission de l'invoquer (lambda:InvokeFunction), à ajouter à la main

Les réflexes pour l'examen

  1. Simple passage vers Lambda, au moindre coût → HTTP API. Besoin d'API keys, usage plans, cache, mock ou API privée → REST API.
  2. Échange bidirectionnel en temps réel (chat, direct) → WebSocket API avec ses route keys.
  3. Clients répartis dans le monde → edge-optimized. Accessible seulement depuis un VPC → private. Les deux sont REST seulement.
  4. Lambda proxy → renvoyer statusCode, headers, body (chaîne). Sinon erreur 502.
  5. Transformer requête et réponse sans toucher la Lambda → intégration non-proxy avec templates VTL.
  6. Appeler SQS ou Step Functions sans Lambda → intégration directe vers le service AWS.
  7. Migrer un monolithe petit à petit → intégration HTTP proxy, route par route.
  8. Atteindre un ALB ou NLB privé dans un VPC → VPC Link.
  9. Une API, plusieurs environnements → stages et variables de stage (alias Lambda).
  10. Tester une nouvelle version sur un peu de trafic réel → déploiement canary (percentTraffic).
  11. Changement d'une API REST invisible → redéployer sur le stage.
  12. Erreur 429 → throttling. Limiter par client → usage plan avec API key et quota.
  13. Restreindre par IP ou par compte → resource policy (REST seulement). Bloquer injections SQL, XSS, pays → WAF.
  14. Le backend doit vérifier que l'appel vient d'API Gateway → certificat client. Authentifier le client lui-même → mTLS sur domaine personnalisé.
  15. Utilisateurs d'une app → Cognito / JWT. Logique de jeton sur mesure → Lambda authorizer. Appelants AWS → IAM.
  16. Une API key n'est pas un mécanisme de sécurité.
  17. Erreur CORS dans le navigateur → activer CORS (preflight OPTIONS). Avec Lambda proxy, la Lambda renvoie elle-même les en-têtes.
  18. 502 → réponse Lambda mal formée. 504 → timeout (29 s). 403 « Missing Authentication Token » → mauvaise route.
  19. Latency contre IntegrationLatency pour situer la lenteur. Suivre une requête à travers les services → X-Ray. Qui a modifié la config → CloudTrail. Conformité → Config.
  20. Réduire les appels backend sur les GET → cache (facturé à l'heure). Réduire la taille des échanges → compression.
