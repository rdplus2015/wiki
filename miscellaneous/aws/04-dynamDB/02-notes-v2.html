DynamoDBNoSQL clé-valeur et document

  • 01Fondamentaux

    • Base NoSQL clé-valeur et document, entièrement managée et serverless (aucun serveur à gérer)
    • Scale horizontalement et automatiquement
    • Supporte ACID grâce aux transactions
    • Facturation : on-demand (par requête) ou provisioned (capacité réservée)
    • Piège Pas de jointures : les données sont dénormalisées, dupliquées volontairement
    • Côté AWS : RDS pour le relationnel ; DynamoDB, ElastiCache, Neptune pour le non relationnel
    RelationnelleNoSQL
    ExemplesSQL Server, OracleRedis, MongoDB, DynamoDB
    SchémaStrict, défini d'avanceFlexible, dynamique
    ScalingVertical (serveur plus gros)Horizontal (plus de nœuds)
    Choisir siSchéma strict, requêtes complexes, pas de perf R/W extrêmeScale horizontal, paires clé-valeur, schéma dynamique, très gros débit

  • 02Composants et types de données

    • Table = collection d'items (≈ table SQL, sans schéma fixe)
    • Item = un enregistrement (≈ ligne), un ensemble d'attributs
    • Attribut = un champ (≈ colonne)
      • Un item peut avoir des attributs qu'un autre item de la même table n'a pas
    • Seule la clé primaire est obligatoire
    • Piège Taille max d'un item : 400 KB (noms + valeurs d'attributs)
    • Scalaires (une seule valeur) : String, Number, Binary, Boolean, Null
    • Sets (plusieurs valeurs scalaires du même type) : String Set, Number Set, Binary Set
    • Documents (structures imbriquées type JSON) : List, Map

  • 03Clés primaires et partitionnement

    • Clé simple : partition key seule (hash attribute), unique pour chaque item
    • Clé composite : partition key + sort key
      • La partition key seule peut se répéter
      • La combinaison PK + SK doit être unique
    • Pas d'auto-incrément : on utilise un UUID ou un ID applicatif
    • La valeur hashée de la PK décide de la partition (allocation de stockage)
    • Items de même PK stockés ensemble, triés par SK
      • Un Query sur une PK lit un bloc contigu : c'est ce qui le rend rapide
    • Piège Hot partition : une PK qui reçoit trop de trafic limite tout, même si la table est sous sa capacité
      • Bonne PK = forte cardinalité, trafic réparti
    • Précision « Chaque valeur de PK a sa propre partition » est une simplification : plusieurs valeurs peuvent partager une partition physique (limite ≈ 10 GB, 3 000 RCU, 1 000 WCU par partition)

  • 04Index secondaireschercher autrement que par la clé primaire

    Pourquoi

    • Sans index, on ne cherche que par la clé primaire
    • Un index définit une clé alternative pour interroger sur un autre attribut
    • Pour l'utiliser : Query avec IndexName

    GSI contre LSI

    GSILSI
    PortéeAu-delà de la partition (toutes les partitions)Dans la même partition
    ClésPK et SK différentes de la tableMême PK, SK différente
    DébitRCU/WCU propresPartagé avec la table
    TaillePas de limite10 GB par valeur de PK
    CréationÀ tout momentSeulement à la création de la table
    Maximum20 par table5 par table
    LectureEventually consistent seulementSupporte strongly consistent

    Un LSI enferme les données d'une PK dans une seule partition (10 GB max). Si ça peut déborder, il faut prévoir un GSI dès le design.

    Projection : quoi copier dans l'index

    • KEYS_ONLY : seulement les clés
    • INCLUDE : clés + attributs choisis
    • ALL : tous les attributs
    • Bonne pratique : projeter le minimum (moins de coût et de latence)

    Choisir la clé d'un GSI

    • Un GSI regroupe des items venant de partitions différentes. Exemple : status (LEGIT / FRAUD / PENDING) permet « tous les items avec status = X, tous users confondus », impossible avec la PK/SK de la table
    • La SK du GSI (ex. created_at) trie chaque groupe. Une SK qui varie par item est normale
    • Précision Une PK de GSI à très peu de valeurs concentre les écritures et peut créer une hot partition
      • Un GSI en throttling fait aussi throttler les écritures de la table de base
      • Parade : ajouter un suffixe de sharding ou combiner la valeur avec une date

    Sparse index

    • Seuls les items qui possèdent l'attribut clé de l'index y apparaissent
    • Utile pour un index léger : ne remplir l'attribut que quand status = PAID

  • 05Opérations de l'API

    Les 4 catégories

    • Contrôle : créer et gérer les tables (CreateTable : nom, schéma de clés, définition des attributs, débit provisionné)
    • Données (CRUD) : PutItem, GetItem, UpdateItem, DeleteItem, Query, Scan
    • Batch : BatchGetItem, BatchWriteItem
    • Transaction : TransactWriteItems, TransactGetItems, changements coordonnés, tout ou rien, sur une ou plusieurs tables

    Lire

    OpérationClé requiseRôle
    GetItemClé primaire complète (PK + SK si composite)Un seul item. Eventually consistent par défaut
    QueryPK obligatoire (+ condition sur la SK)Tous les items d'une PK. Plus efficace que Scan. Table ou index
    ScanAucuneParcourt toute la table ou l'index. Coûteux, à éviter en prod

    Écrire

    • DeleteItem : supprime un item par sa clé primaire
    • Condition Expressions : s'appliquent aux écritures, l'opération n'a lieu que si la condition est vraie
    • Ajouter un attribut plus tard à un item existant : UpdateItem, sans migration

  • 06Cohérence de lecture et transactions

    Cohérence

    • Les données sont copiées sur plusieurs serveurs : la synchronisation prend environ 1 s, d'où un possible décalage à la lecture
    • Eventually consistent (défaut) : peut renvoyer une valeur périmée, 0,5 RCU par 4 KB, moins cher
    • Strongly consistent : reflète la dernière écriture confirmée, 1 RCU par 4 KB, plus cher
      • Paramètre ConsistentRead = true
    • Piège Un GSI ne fait que de l'eventually consistent. Un LSI et la table peuvent faire du strongly

    Transactions ACID

    • TransactWriteItems : Put / Update / Delete, avec éventuelles conditions, en un bloc tout ou rien
    • TransactGetItems : plusieurs lectures cohérentes ensemble
    • Si une opération ou une condition échoue, toute la transaction est rejetée, rien n'est appliqué à moitié
    • Coût doublé par rapport à une opération normale (voir branche 13)

  • 07Débit et capacitéRCU, WCU et choix du mode

    Les 2 modes

    • Provisioned : tu fixes les RCU et WCU à l'avance. Moins cher pour un trafic stable, élevé et prévisible
    • On-demand : DynamoDB s'adapte tout seul, facturé à la requête. Idéal pour un trafic imprévisible ou en pics, ou sans envie de planifier
      • Les unités s'appellent RRU / WRU, mêmes tailles (4 KB / 1 KB)

    Définitions

    • RCU = 1 lecture strongly consistent par seconde pour 4 KB (ou 2 lectures eventually)
    • WCU = 1 écriture par seconde pour 1 KB
    • 3 infos pour calculer : nombre d'opérations par seconde, taille moyenne des items, type de cohérence

    Formules

    RCU strongly   = arrondi↑(taille ÷ 4 KB) × lectures/s
RCU eventually = arrondi↑(taille ÷ 4 KB) × lectures/s ÷ 2
WCU            = arrondi↑(taille ÷ 1 KB) × écritures/s
    • Piège On arrondit toujours la taille au supérieur avant de multiplier

    Exemples

    CasCalculRésultat
    4 KB, strongly, 30 lectures/s1 × 3030 RCU
    4 KB, eventually, 30 lectures/s1 × 30 ÷ 215 RCU
    6 KB, strongly, 10 lectures/s2 × 1020 RCU
    8 KB, strongly, 1 lecture/s2 × 12 RCU
    1 KB, 14 écritures/s1 × 1414 WCU
    2,5 KB, 10 écritures/s3 × 1030 WCU

    En production

    • Démarrer en on-demand
    • Observer environ 2 semaines dans CloudWatch : RCU/s, WCU/s, taille des items
    • Si le trafic est prévisible, passer en provisioned
    • Demande qui explose → erreur 400 (ProvisionedThroughputExceededException) → Auto Scaling ou retour en on-demand

  • 08Streams

    • Flux, dans l'ordre chronologique, de toutes les modifications d'une table : insert, update, delete
    • Piège Conservé 24 h seulement
    • Option à activer sur la table
    • Chaque modification produit un stream record : le changement, qu'une application peut lire pour réagir
      • Type d'événement : INSERT, MODIFY, REMOVE
      • Un SequenceNumber garde l'ordre
      • Les records sont regroupés en shards

    Les 4 types de vue

    TypeContenu du record
    KEYS_ONLYLes clés de l'item modifié
    NEW_IMAGEL'item après modification
    OLD_IMAGEL'item avant modification
    NEW_AND_OLD_IMAGESLes deux

    Usages

    • Déclencher une Lambda à chaque écriture (event-driven)
    • Réplication (base des Global Tables)
    • Audit, synchronisation entre systèmes, Kinesis

  • 09Global Tables

    • Table répliquée automatiquement dans plusieurs régions AWS, une réplique par région, copie identique, via les Streams
    • Base multi-région et multi-active : lecture et écriture dans chaque région, sans construire sa propre réplication
    • On choisit les régions où la table doit être disponible
    • Mise à jour propagée en quelques secondes
    • Conflit (même item écrit dans 2 régions) : last writer wins, selon l'horodatage
    • Piège Lecture strongly consistent seulement dans la région où l'écriture a eu lieu ; entre régions, c'est eventually
    • Précision Les transactions ACID ne valent que dans la région où elles s'exécutent, pas d'une région à l'autre
    • Précision Depuis 2025, mode optionnel MRSC (multi-Region strong consistency) : lectures fortes entre régions, aucune perte de données (RPO zéro)
      • Le mode par défaut, MREC (eventual consistency), garde le last writer wins

  • 10Sauvegarde et restauration

    Backup on-demand

    • Sauvegarde complète de la table, pour la rétention longue durée et la conformité
    • Asynchrone, aucune limite de nombre, n'affecte pas le débit de la table

    PITR (Point-in-time recovery)

    • Sauvegarde continue, rien à planifier
    • Restaure la table à n'importe quel moment des 35 derniers jours
    • Protège contre une écriture ou suppression accidentelle (ex. un script de test lancé sur la prod)
    • Piège Désactivé par défaut, à activer table par table
    • Piège Toute restauration crée une nouvelle table, elle n'écrase jamais la source
    • Backup et restauration se déclenchent depuis la console, la CLI ou l'API

  • 11Conception single-tablepartir des requêtes, puis dessiner les clés

    Démarche

    • Access patterns d'abord : quelles requêtes l'application fait vraiment ? Les clés sont conçues pour les servir
    • Single-table : plusieurs types d'entités dans une seule table (ex. profil d'un user et ses transactions)
    • Avantage : profil et transactions en un seul Query, sans jointure ni aller-retour multiple
    • Coût : plus d'effort de design au départ

    Les clés

    PK : USER#<user_id>
SK : PROFILE
SK : TXN#<timestamp ISO 8601>#<id>
    • PK partagée : tout ce qui appartient à un user est dans la même partition
    • Le préfixe USER# évite les collisions avec une autre entité qui réutiliserait le même ID
    • PROFILE : valeur fixe, il n'y en a qu'un par user
    • TXN#... : valeur variable, un user en accumule beaucoup

    Pourquoi cet ordre dans la SK

    • Timestamp ISO 8601 en premier : l'ordre alphabétique égale l'ordre chronologique, donc un Query renvoie les items triés sans tri côté client
    • ID à la fin : garantit l'unicité même si deux items naissent à la même milliseconde (départage)

    GSI status-index

    GSI partition key : status
GSI sort key      : created_at
    • Permet « tous les items avec status = X », tous users confondus
    • created_at trie chronologiquement dans chaque groupe
    • Un GSI s'ajoute après coup, un LSI non
    • Précision Voir la mise en garde sur les clés de GSI à faible cardinalité (branche 04)

    Sans schéma, et relations

    • Un attribut s'ajoute plus tard avec UpdateItem, sans migration (contrairement à ALTER TABLE)
    • Principe du minimum : pas de nom ni d'email dans le profil si un fournisseur d'identité les gère déjà
    • Many-to-many : un item de relation dont la SK sert de PK au GSI (et inversement), interrogeable dans les deux sens
    • Piège Hot partition aussi ici : un user extrêmement actif peut saturer sa partition

  • 12Déboguer une Lambda qui utilise DynamoDB

    Où regarder

    • Une Lambda n'a pas de terminal : ses print et exceptions n'apparaissent que dans CloudWatch Logs
    • Un groupe de logs par fonction : /aws/lambda/<nom-fonction>, un log stream par invocation
    • Démarche : erreur côté client (API Gateway cache tout derrière un « Internal server error » générique) → groupe de logs → stack trace → correction → redéploiement → test

    Piège 1 : Decimal non sérialisable

    • boto3.resource renvoie les nombres en Decimal (Query, Scan, GetItem) pour garder la précision
    • json.dumps plante : TypeError: Object of type Decimal is not JSON serializable
    from decimal import Decimal

def decimal_default(obj):
    if isinstance(obj, Decimal):
        return int(obj) if obj % 1 == 0 else float(obj)
    raise TypeError(f"{type(obj)} non sérialisable")

json.dumps(data, default=decimal_default)
    • Utile seulement dans les fonctions qui lisent. Une fonction qui n'écrit que (put_item) n'en a pas besoin, et l'ajouter sans la définir donne un NameError

    Piège 2 : import oublié

    • Utiliser Decimal sans from decimal import Decimal donne NameError: name 'Decimal' is not defined, une erreur qui semble sans rapport avec le bug d'origine
    • Réflexe : quand un code référence un type, vérifier son import

    Piège 3 : CORS avec Lambda proxy

    • La requête réussit côté serveur (200) mais le navigateur la bloque
    • Le bloc Cors du template SAM ne génère les en-têtes que pour la réponse OPTIONS (preflight), pas pour la vraie réponse
    • La Lambda doit renvoyer elle-même les en-têtes CORS, sur tous ses chemins, erreurs comprises
    • Piège Un preflight réussi ne prouve pas que la vraie requête passera
    return {
  "statusCode": status_code,
  "headers": {
    "Access-Control-Allow-Origin": "*",
    "Access-Control-Allow-Headers": "Content-Type",
    "Access-Control-Allow-Methods": "GET,POST,OPTIONS"
  },
  "body": json.dumps(data)
}

  • 13Hors de tes notesà connaître pour le DVA-C02

    Lire sans gaspiller

    • Piège Query et Scan renvoient au max 1 MB par appel : paginer avec LastEvaluatedKey → ExclusiveStartKey
    • KeyConditionExpression : PK = et SK (begins_with, between, <, >)
    • FilterExpression s'applique après la lecture : les RCU sont consommés pour tous les items lus, pas seulement ceux gardés
    • ProjectionExpression réduit ce qui est renvoyé, pas le coût de lecture

    Écrire en sécurité

    • ConditionExpression (ex. attribute_not_exists(PK)) : si fausse, ConditionalCheckFailedException
    • Compteur atomique : UpdateItem avec SET n = n + :inc
    • Verrouillage optimiste : attribut version et condition version = :v à l'écriture, pour éviter les écrasements concurrents

    Batch et transactions : limites

    • BatchWriteItem : 25 Put/Delete max (pas d'Update), 16 MB
    • BatchGetItem : 100 items max, 16 MB
    • Items refusés → UnprocessedItems à relancer avec exponential backoff
    • Transaction : max 100 actions, 4 MB
    • Piège Une opération transactionnelle coûte 2× : 2 RCU par 4 KB lus, 2 WCU par 1 KB écrit

    Erreurs et capacité

    • ProvisionedThroughputExceededException (400) → retry avec exponential backoff (les SDK le font seuls) ; les erreurs 5xx aussi
    • Auto Scaling : ajuste les RCU/WCU provisionnés autour d'une utilisation cible (ex. 70 %)

    TTL

    • Un attribut Number en secondes epoch : une fois dépassé, l'item est supprimé
    • Suppression en arrière-plan, pas instantanée (quelques heures à quelques jours)
    • Gratuite (aucun WCU consommé), et visible dans les Streams

    DAX

    • Cache en mémoire devant DynamoDB, latence en microsecondes, compatible avec l'API DynamoDB
    • Pour les lectures répétées et les points chauds
    • Piège Sert les lectures eventually consistent ; une lecture strongly consistent le contourne

    Divers

    • Piège Item > 400 KB impossible : stocker le gros contenu dans S3 et garder la référence dans DynamoDB
    • PartiQL : requêtes de style SQL sur DynamoDB
    • Export vers S3 (depuis PITR), sans consommer de capacité de lecture
    • Classes de table : Standard et Standard-IA (données rarement lues)

Les réflexes pour l'examen

  1. Chercher par un attribut qui n'est pas la clé → index secondaire (GSI, ou LSI si même PK avec une autre SK).
  2. Index à ajouter sur une table déjà créée → GSI. Un LSI se définit à la création.
  3. Lecture strongly consistent sur un index → LSI seulement. Un GSI est toujours eventually.
  4. Lecture à jour obligatoire → ConsistentRead = true (1 RCU / 4 KB). Défaut : eventually (0,5 RCU).
  5. Calcul RCU / WCU → arrondir la taille au supérieur (4 KB / 1 KB), eventually = ÷ 2.
  6. Transaction → coût ×2, tout ou rien.
  7. Scan à éviter. Utiliser Query avec la PK, ou Query sur un index.
  8. FilterExpression ne réduit pas les RCU consommés.
  9. Hot partition → PK à forte cardinalité, trafic réparti.
  10. ProvisionedThroughputExceededException (400) → exponential backoff, Auto Scaling ou on-demand.
  11. Trafic imprévisible → on-demand. Stable et prévisible → provisioned.
  12. Réagir à chaque écriture → Streams + Lambda (24 h de rétention).
  13. Multi-région, multi-active → Global Tables (last writer wins).
  14. Erreur accidentelle sur la prod → PITR (35 jours), qui crée une nouvelle table.
  15. Expirer des données automatiquement → TTL.
  16. Cache en microsecondes devant DynamoDB → DAX.
  17. Item > 400 KB → S3 pour le contenu, référence dans DynamoDB.
  18. Écrasements concurrents → écriture conditionnelle (verrouillage optimiste).
  19. Lambda qui lit DynamoDB puis json.dumps → convertir les Decimal.
  20. CORS avec Lambda proxy → en-têtes dans la réponse de la Lambda, pas seulement dans le preflight.
